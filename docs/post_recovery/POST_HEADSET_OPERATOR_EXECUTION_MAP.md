## 11. Operator packet template

Every implementation PR must state:

1. **Outcome:** one player-visible or foundational result.
2. **Preconditions:** exact merged packets and proof levels.
3. **Owner:** canonical system and operator lane.
4. **Files claimed:** exact paths.
5. **Forbidden files/owners:** explicit.
6. **Data flow:** source → owner → observer/presentation → saved outcome.
7. **Tests:** pure/EditMode/PlayMode/audit as applicable.
8. **Device campaign:** exact actions and pass/fail criteria when device-sensitive.
9. **Diagnostics:** stable `ZIPTIDE:` tokens.
10. **Rollback:** one commit/flag/data removal that restores the prior behavior.
11. **Proof lane:** ordinary, PlayMode, Golden Android, clean package or Quest.
12. **Definition of done:** includes player-visible/device evidence when required.

No PR is done because its self-authored unit test passes. Tests must prove behavior at the correct ownership seam and the required physical-device evidence must exist.

## 14. Stop conditions

An operator stops and escalates when:

- the headset checkpoint fails;
- a canonical owner is unclear or duplicated;
- the requested change requires a protected-file mutation not declared in the packet;
- the contract and runtime disagree about beat order or signal meaning;
- CI is red for the lane's source;
- three attempted fixes fail without narrowing the same defect class;
- a scene requires manual YAML editing;
- a device-sensitive claim lacks a device campaign;
- scope expands beyond the packet's outcome;
- a later horizon plan is being pulled ahead of its prerequisite rung.

## 15. Definition of a project that another LLM can continue

The project is operator-ready when:

- one current execution map exists;
- every active packet has exact dependencies, owners, files, tests, device steps and rollback;
- machine-readable contracts define player experience order;
- subsystem plans define closed vocabularies and forbid parallel owners;
- status documents match source truth;
- every feature has a proof level and visible acceptance criterion;
- the next operator can read the map, claim one bounded packet and begin without redesigning the game.

This map aims to reach that condition. It does not pretend autonomous end-to-end game completion is realistic; it makes human judgment concentrate on taste, device feel and canon rather than rediscovering architecture.
